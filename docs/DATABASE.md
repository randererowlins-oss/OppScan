# 🗄️ DATABASE — schema, seed data & the road to Postgres

> OppScan persists to a **zero-dependency JSON document store**:
> `backend/data/db.json`, owned entirely by `backend/src/db.ts`.
> This doc explains the schema, the guarantees, and exactly how to swap in
> Postgres later without touching a single route.

---

## 1 · Why a JSON file? (and why it's fine *for now*)

| Requirement | JSON store | Postgres |
|-------------|-----------|----------|
| Runs with zero setup (local, CI, sandbox) | ✅ | ❌ needs a server |
| Human-inspectable data | ✅ open the file | needs a client |
| Atomic single-writer saves | ✅ tmp-write + rename | ✅ |
| Concurrent writers / >100k rows / SQL joins | ❌ | ✅ |

Access pattern today: small collections, one Node process, modest traffic.
The right call is the boring one — and the persistence surface is **one file**,
so upgrading later is a contained job (§ 6).

---

## 2 · File layout & guarantees

- **Path:** `backend/data/db.json` (override with `DB_FILE`). Gitignored —
  each environment owns its data.
- **First boot:** if the file is missing or corrupt, `seedDatabase()` generates
  fresh demo content and writes it immediately.
- **Reads:** served from memory (loaded once at boot) — effectively instant.
- **Writes:** mutate in memory → `store.save()` → write `db.json.tmp` →
  atomic `rename` to `db.json`. Readers never see half-written JSON; a crash
  mid-write leaves either the old or the new file, never garbage.
- **Reset:** `npm run seed` (backend) wipes + reseeds. Dev only.

```ts
// backend/src/db.ts — the entire persistence API:
store.data    // DatabaseShape (mutable)
store.save()  // persist to disk
store.reset() // wipe + reseed
```

## 3 · Schema (5 collections)

```
users  1───∞  opportunities  (postedBy → users.id, nullable: scanner-found have null)
users  ∞───∞  opportunities  via saved  (userId, opportunityId)
sources      (scan origins; opportunities.source stores the source NAME)
scans        (append-only run history)
```

### `users`

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | `user-…` (nanoid) |
| `name` | string | Display name, 2–60 chars |
| `email` | string | Lowercase, **unique** |
| `passwordHash` | string | bcrypt, 10 rounds — never serialized |
| `role` | `"user" \| "admin"` | Only admins hit `/api/admin/*` |
| `avatarColor` | string | Hex for avatar fallback |
| `createdAt` | ISO datetime | |

### `opportunities`

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | `opp-…` |
| `title` / `organization` | string | |
| `type` | `Job·Grant·Tender·Freelance·Funding·Scholarship` | The 6 rails of the app |
| `category` | string | Free-form (`Engineering`, `Climate`…) |
| `description` | string | Plain text, ≥ 60 chars at the boundary |
| `location` / `remote` | string / boolean | |
| `amountMin` / `amountMax` / `currency` | number? / string? | `currency` like `USD`, `EUR` |
| `deadline` | ISO datetime? | `null` = rolling / no deadline |
| `url` | string | Canonical apply link |
| `source` | string | Source **name** (denormalised for easy display) |
| `tags` | string[≤10] | |
| `status` | `open·closing-soon·closed` | |
| `featured` | boolean | Admin-curated → landing page |
| `applicantsCount` / `views` | number | Counters; feed back into `score` |
| `score` | number 0–100 | `computeScore()` — recomputed on view/apply/edit |
| `postedBy` | string? | `users.id` or `null` (scanner) |
| `createdAt` / `updatedAt` | ISO datetime | |

### `saved` (join)

| Field | Type |
|-------|------|
| `userId` | `users.id` |
| `opportunityId` | `opportunities.id` |
| `createdAt` | ISO datetime |

Uniqueness of the pair is enforced in the route (idempotent save).

### `sources`

| Field | Type | Notes |
|-------|------|-------|
| `id` / `name` / `url` | string | `name` is referenced by `opportunities.source` |
| `kind` | `OpportunityType \| "Mixed"` | |
| `status` | `active·paused·error` | Only `active` sources are scanned |
| `lastScanAt` | ISO? | Stamped on every scan run |
| `foundCount` | number | Lifetime listings attributed |

### `scans` (append-only)

| Field | Type |
|-------|------|
| `id` / `startedAt` / `finishedAt` | string / ISO / ISO |
| `sourcesScanned` / `newFound` | number |
| `newIds` | string[] (opportunity ids created by the run) |
| `status` | `"completed"` |

## 5 · Inspecting / editing data by hand

```bash
# Pretty-print counts:
python3 -c "import json; d=json.load(open('backend/data/db.json'));
print({k: len(v) for k, v in d.items() if isinstance(v, list)})"

# Reset to seed state (STOP THE API FIRST — it holds the DB in memory):
cd backend && npm run seed
```

> ⚠️ The API keeps the DB in memory and writes through on change. Editing
> `db.json` while the server runs will be overwritten — stop the server first.

## 6 · Going to production: the Postgres migration recipe

When you outgrow the file (concurrent writers, scale, SQL needs), the swap is
mechanical because **routes only touch `store.data` + `store.save()`**:

1. Add Prisma (`npm i prisma @prisma/client`) and model the 5 tables 1:1 from § 3.
2. Rewrite `db.ts` to expose the **same interface** backed by Prisma:
   - `store.data.users` → `prisma.user.findMany()` (cache per request or keep
     simple: make routes async — they already are where needed)
   - `store.save()` → no-op (writes go straight through)
   - `store.reset()` → `deleteMany` + `seedDatabase()` inserts
3. Move the few in-memory operations (filter/sort/paginate in
   `routes/opportunities.ts`) to Prisma queries with `where/orderBy/take/skip`.
4. Delete nothing else: route signatures, response shapes and the frontend stay
   byte-identical.

Estimated effort: one focused afternoon. Until then, enjoy the zero-ops life.
